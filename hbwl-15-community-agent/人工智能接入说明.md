# 人工智能接入说明

**结论先行：现阶段没必要接入，接入的收益主要不在"答得更好"，而在"答不上来时更体面"。**
但如果要做成"真正的智能体"，接入是迟早的事——本文说明判断依据、成本与正确做法。

---

## 一、先纠正一处文档不准确的地方

之前的 README 写着「配置 `LLM_API_KEY` 即启用大模型增强」。**这个说法是不准确的，现已更正。**

实际情况：代码里保留了 `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` 三个配置位，
以及 `stats()` 的 `llmEnabled` 标志，但**没有任何代码真正发起过大模型请求**。

实测验证：设置 `LLM_API_KEY` 后，`llmEnabled` 显示为 `true`，
但 `ask()` 耗时仍是 **1 ms**，无任何网络请求，回答仍全部来自本地知识库。

**当前版本 100% 离线运行。** 保留那三个配置位只是为了让后续接入不必改动调用方。

---

## 二、当前离线的实际水平

用实测数据说话（`node scripts/selfcheck.js`，49 项全过）：

| 能力 | 表现 |
|---|---|
| 知识库规模 | 62 条（53 条已核实，13 个官方来源） |
| 单次问答耗时 | **112 µs**（约 8900 次/秒） |
| 覆盖的问题类型 | 报修、心理、资助、教务、图书馆、安全、活动、场所等 |
| 意图识别 | 三级路由（紧急 / 列表 / 检索），含回归测试 |
| 答不上来时 | 走兜底，给出引导与联系方式，**不编造** |

**它已经能正确回答大多数高频问题**，且每条回答都可追溯到官方来源。

## 三、离线的三个真实短板

这三类问题，靠加关键词和加条目都解决不好：

### 1. 句式相似但主题不同

| 同学问 | 当前回答 | 问题 |
|---|---|---|
| 怎么办理校园卡 | 图书馆怎么借书 | 靠「校园卡」三字命中，主题不同 |
| 四六级报名时间 | 活动与计划列表 | 「报名」触发了活动意图 |

**我实测过两种更复杂的判据（优势比、主题词整词覆盖），都因误伤正常问题而放弃**：
正常问题可低至 0.015 的优势比、缺口问题可高达 0.80，分布完全重叠；
整词覆盖判据把「学校的校历在哪看」这类正常问题误拦了 2/25。

**词面检索无法可靠完成这个区分**——这正是大模型擅长的（它懂语义，不只是字面）。

### 2. 同义改写认不出

「电脑开不了机」「笔记本黑屏」「机器点不亮」——同一个问题三种说法。
现在必须在 `tags` 里逐个列出，**漏一个就查不到**。

### 3. 多轮对话做不到

同学问「自习室怎么预约」→ 回答后追问「那开放到几点」——当前是单轮问答，
第二句会被当成新问题独立检索。

## 四、接入的收益与代价

### 收益

| 收益 | 说明 | 是否值得 |
|---|---|---|
| **兜底更体面** | 答不上来时，由大模型基于检索到的相关条目组织回答，而不是一句"没找到" | ⭐ 最实在的收益 |
| 同义改写理解 | 不必穷举 tags | 中等 |
| 多轮对话 | 支持追问 | 中等 |
| 回答更自然 | 语气更口语化 | 一般 |

### 代价（这些是真实的）

| 代价 | 说明 |
|---|---|
| **可能编造** | 大模型会"一本正经地胡说"。社区场景里，编造的办事流程会让同学**白跑一趟** |
| **需要外网** | 一体机若断网，功能直接失效 |
| **需要 API Key 与费用** | 按调用量计费，需学院审批与预算 |
| **数据出校** | 同学的问题会发送到校外服务器，**涉及隐私与合规** |
| **响应变慢** | 从 112 µs 变成 1–3 秒 |
| 破坏零依赖 | 需要网络配置、密钥管理 |

### 关键判断

> **对社区服务场景，"答错"比"答不上来"代价更高。**
>
> 答不上来时同学会去问辅导员；答错了同学会照着做，然后白跑一趟。
> 所以**不能把大模型直接放到回答位置**，只能放在"兜底组织语言"的位置。

---

## 五、推荐做法：检索增强，而非替代

如果决定接入，**正确架构是「检索优先 + 大模型只做兜底润色」**：

```
同学提问
   ↓
① 本地 BM25 检索
   ↓
② 置信度足够？──是──→ 直接返回知识库原文（不经过大模型，保证准确）
   │
   否
   ↓
③ 取检索到的相关条目作为上下文，交给大模型组织回答
   ↓
④ 回答末尾强制标注：「以下内容由 AI 生成，未经核实，请以学院正式通知为准」
```

### 三条不可让步的红线

1. **紧急场景（诈骗/火灾/急救）绝不经过大模型** —— 必须走固定处置流程
   （现在已是如此，接入后必须保持）

2. **已核实内容不经过大模型** —— 知识库里有明确答案时，直接返回原文。
   大模型只处理"知识库没有直接答案"的情况

3. **AI 生成的回答必须显式标注** —— 不能让同学分不清哪句是官方信息、哪句是 AI 推测

## 六、如果接入，怎么接（工作量很小）

现有代码已为此留好位置，**改动集中在两个文件**：

### 1. `lib/agent.js` —— 增加一个方法

```js
async askWithLLM(question, hits) {
  const context = hits.slice(0, 3).map(h => {
    const r = h.doc.raw;
    return `【${r.title || r.question}】\n${r.content || r.answer}`;
  }).join('\n\n');

  const res = await fetch(`${this.llmBase}/chat/completions`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${this.llmKey}`,
    },
    body: JSON.stringify({
      model: this.llmModel,
      messages: [
        { role: 'system', content:
          '你是湖北文理学院15栋社区智能体的助手。' +
          '只能依据下面提供的资料回答，资料没有的内容必须说"资料中没有相关信息"，' +
          '绝不编造办事流程、电话或日期。' },
        { role: 'user', content: `资料：\n${context}\n\n问题：${question}` },
      ],
      temperature: 0.3,   // 低温度，减少发挥
    }),
  });
  const data = await res.json();
  return data.choices[0].message.content;
}
```

### 2. `server.js` —— 在兜底分支调用

```js
// 置信度不足时：有 API Key 就走大模型，否则走原有兜底
if (!top || top.score < 2.0) {
  if (agent.llmKey && hits.length) {
    const text = await agent.askWithLLM(question, hits);
    return sendJSON(res, 200, {
      text: text + '\n\n---\n⚠️ **以上内容由 AI 生成，未经学院核实，请以官方通知为准。**',
      intent: 'llm-fallback',
      verified: false,        // 明确标记未核实
      aiGenerated: true,      // 前端可据此显示特殊样式
    });
  }
  return agent.fallbackReply(question, hits);
}
```

**工作量估计**：半天以内（含联调）。存储层、检索层、前端都不用改。

## 七、建议的推进节奏

| 阶段 | 做什么 | 为什么 |
|---|---|---|
| **现在** | **不接入** | 62 条知识库已覆盖高频问题；离线快、准、可追溯；一体机可能没网 |
| 试运行 1–2 个月 | 用教师端看板收集「未命中问题」 | 用**真实数据**判断缺口有多大，而不是凭感觉 |
| 缺口多且集中在"表述差异" | 考虑接入，走检索增强方案 | 这类问题大模型确实擅长 |
| 缺口多但集中在"内容缺失" | **继续补知识库，不必接大模型** | 缺内容就该补内容，大模型也编不出来 |

### 判断标准（用看板数据决策）

打开教师端 → 数据看板 → 「未命中问题」：

- 若**未命中很少**（每天个位数）→ 不需要大模型
- 若**未命中多，且多为同义改写**（如各种"电脑坏了"的说法）→ 值得接入
- 若**未命中多，且为知识库确实没有的内容**（如"校车时刻表"）→ 补内容，不是接模型

> 顺带一提：现在**已经有这个看板了**，接入决策可以完全基于真实数据，不必猜测。

---

## 八、如果决定接入，需要先确认的三件事

1. **网络**：一体机能否稳定访问外网？断网时必须有降级方案（现在天然就是降级方案）
2. **费用**：按调用量计费，需学院审批。可先估算：一天 500 次提问 × 每次约 500 token ≈ 25 万 token/天
3. **合规**：同学的问题会出校。**建议向学院信息化中心报备**，并在界面明示"部分回答由 AI 生成"

---

## 九、一句话总结

**现在不必接。** 当前的离线方案在准确性、速度、可追溯性上更适合社区服务场景，
而且**接入的主要收益不是"答得更好"，而是"答不上来时更体面"**。

等试运行一段时间、拿到真实的「未命中问题」数据后再决定——
如果那时发现缺口集中在"表述差异"，接入是值得的；如果集中在"内容缺失"，那就该继续补知识库。

**决策依据已经在教师端看板里了，不必凭感觉判断。**
